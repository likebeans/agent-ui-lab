# 从学习实验到真实开发

先确定一个业务闭环，比如“用户提出出行需求 → Agent 查询可选方案 → 展示表单 → 用户确认 → 服务端保存方案”。不要一开始就把所有协议串起来。

## 1. 选对需要的能力

| 需要                                         | 建议起点                             |
| -------------------------------------------- | ------------------------------------ |
| 流式回答、工具执行进度、Agent 与页面共享状态 | AG-UI                                |
| Agent 根据情境选择前端组件和布局             | A2UI                                 |
| MCP 工具自带一个交互界面，在兼容 Host 中运行 | MCP Apps                             |
| 一个固定表单加一个普通业务 API               | 先用现有前端和 API，不必强行引入协议 |

## 2. 替换 Agent 决策层

本项目的 Agent 是确定性代码。`shared/chat-agent.ts` 负责选择本轮协议及解析城市、天数，`src/ChatWorkspace.tsx` 负责组织消息和共享上下文。`shared/` 中的协议生成与校验逻辑由本地服务和静态学习版共用；`server/` 提供真实 HTTP / SSE 路由。接模型时可以先在服务端替换决策与生成函数，保留这些边界。

当前对话会把过去的文字与界面操作摘要传给 AG-UI 运行，A2UI 和 MCP Apps 使用明确的旅行上下文。它尚未实现由模型自行规划、任意工具组合或长期记忆。真实模型应该只接在服务端：

```text
浏览器 → 你的服务端 → Agent / 模型 SDK
                 ↘ 业务工具 → 数据源
Agent / 业务结果 → 协议适配 → 浏览器
```

接入步骤：

1. 在服务端引入所选模型提供方的官方 SDK，密钥只留在服务端环境变量中。
2. 将模型的文本流转换为 AG-UI 文本事件。将模型工具调用、你实际执行工具的结果分别转换为对应事件。
3. 用服务端业务状态产生 `STATE_SNAPSHOT` 和 `STATE_DELTA`。不要让模型直接决定权限、订单是否生效或资金余额。
4. 把输入校验、超时、取消、失败路径一起接上。模型 HTTP 流结束不一定等于任务成功。
5. 如果要生成 A2UI，提供固定版本的 schema、受支持的组件目录和示例，先验证结构，再给客户端渲染。

这个项目不包含模型 API 的已验证适配器。接入时请查对应提供方的当前 SDK 文档，先做一个最小集成测试；不要把教学中的固定回复称为真实模型输出。

## 3. 固定协议版本和组件契约

A2UI 的协议版本、组件 catalog、客户端渲染能力必须一起锁定。新组件先在目录里定义、校验和实现，再允许 Agent 使用它。遇到未知组件应明确报错或使用可说明的降级，而不是悄悄执行外来代码。

AG-UI 要保留 `threadId`、`runId`、`messageId` 和 `toolCallId` 的关联。断流后的重试和回放需要服务端策略；SSE 本身不会让业务操作变成幂等。

MCP Apps 要协商宿主能力。App 发起工具调用需要宿主授权、服务端鉴权与业务参数校验；不能因为消息来自 iframe 就信任它。

## 4. 从内存状态走向持久状态

区分三层：

- **界面瞬时状态**：输入框、展开项、当前选中的消息。可以留在 React。
- **任务与会话状态**：线程、正在执行的步骤、用户确认。应由服务端管理，按需要存储。
- **业务事实**：预订、订单、账户资料。由业务系统决定，通过受验证的工具读取和变更。

为写操作增加幂等键或业务唯一约束。同一个 `runId` 或 JSON-RPC `id` 只是关联标识，不会自动防止重复下单。用户刷新或网络断开时，应有明确的重新查询入口。

## 5. 准备部署

项目提供两种运行模式，使用相同的确定性生成逻辑、协议 schema、reducer、Renderer 与 AppBridge。

| 模式         | 启动 / 构建                                    | 实际边界                                                                                                    |
| ------------ | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 本地协议模式 | `npm run dev`，或 `npm run build && npm start` | HTTP / SSE、MCP Streamable HTTP、iframe `postMessage`                                                       |
| 静态学习模式 | `npm run build:pages && npm run preview:pages` | AG-UI / A2UI 在浏览器内处理；官方 MCP Client / Server 用 `InMemoryTransport`；iframe `postMessage` 真实执行 |

静态学习版顶部会说明运行模式。协议检查器中 `transport: browser-memory` 和 `client→browser-agent` / `browser-agent→client` 表示进程内教学调用，`POST /api/...` 是对应逻辑路由的标签，不是已发生的 HTTP 请求。MCP 的 `resources/read` 从构建时生成的 `mcp-app/cards.html` 或 `mcp-app/list.html` 读取资源；App / Host 握手与工具代理仍通过官方 SDK 执行。取消会产生真实协议终态；中断本地流只会截断传输。它可以演示协议机制，但不能验证网络代理、服务端隔离或鉴权。

GitHub Pages 使用 `.github/workflows/deploy-pages.yml`，由 Pages 的 `base_path` 配置静态资源前缀，构建后先在无 API 的环境运行浏览器验证，再发布 `dist/`。仓库根目录须包含本项目的 `package.json` 和工作流；在 Settings → Pages 选择 GitHub Actions，推送 `main` 或手动运行工作流即可。具体命令见 [项目部署说明](../README.md#部署与-github-pages)。

本地 `npm start` 仅在本机 3100 端口运行构建产物。真正部署带后端的应用时，先运行 `npm run check`，再具体补齐：

- HTTPS、正确的反向代理流式传输设置，避免 SSE 被代理缓冲。
- 身份认证、会话隔离、请求限额、服务端超时和取消传播。
- 对 A2UI 的 schema / catalog 做版本管理；对 JSON Patch 做完整校验。
- MCP Apps Web Host 按规范使用独立源的 Sandbox Proxy + 内层 App 双 iframe，并通过 HTTP 响应头落实 CSP。当前教学 Host 的单 opaque iframe 与 HTML meta CSP 是简化方案；只授予实际需要的工具与能力。
- 日志中保留关联 ID，并处理敏感字段；协议检查器不应直接向所有产品用户暴露内部载荷。
- 浏览器端错误、工具失败、模型拒绝或截断都有可恢复的 UI。

## 推荐的第一个真实功能

做一个“活动报名助手”：Agent 查询可用活动，A2UI 展示已验证的活动与表单，用户提交后服务端保存报名。先不引入支付。在需求确实需要 MCP 客户端复用时，再把活动浏览器做成 MCP App。

判断是否完成的标准不是“画面很像 AI 产品”，而是可以说清一次请求中：谁决定、谁验证、谁执行、谁展示、失败后怎么恢复。
