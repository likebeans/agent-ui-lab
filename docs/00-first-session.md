# 第一次学习：30 分钟对话

本地运行时，浏览器打开 <http://127.0.0.1:5173>，编辑器打开这个项目；也可访问部署后的 Pages 静态学习版。首页是一个 Agent 聊天框。先用同一段旅行对话体验三种界面能力，再沿协议消息追到代码。当前 Agent 使用确定性规则和样本数据，无需 API Key。

本章默认描述本地 HTTP / SSE 模式。静态版的操作步骤相同，但事件、表单动作和 MCP 工具在浏览器内执行，没有 `/api` 或 `/mcp` 网络请求；iframe 握手仍真实运行。界面顶部和 trace 的传输标记会说明区别，详见 [运行与部署模式](04-real-development.md#5-准备部署)。

下面 30 分钟是建议安排，先走最小流程；不同开发者的实际耗时需要记录。每一步先预测结果，再操作并找证据，不必一开始读完所有 JSON。完整的声明修改与资源对照实验可继续按 [动手学习指南](07-learning-method.md) 完成。若由维护者主持首次学习，使用 [读者验收任务与观察模板](09-learning-validation.md) 记录证据、帮助与卡点；目前尚未实际招募或观察读者，不能把 30 分钟视为已验证的完成时间。

## 0–10 分钟：事件怎样变成回复

发送：**“帮我规划杭州三日游，喜欢慢节奏”**。

这条回复会逐步出现文字、任务进度、工具调用和行程。点击“暂停展示并观察”，后台仍会继续接收真实 SSE，界面停在当前事件。展开“事件如何变成这条回复”，单步回放并比较改变的字段。也可以点击文字或卡片旁的“追溯”入口，反向找到对应事件，再定位检查器中的原始消息。

先回答面板内的“文本增量是追加还是替换？”预测题，再点击“用本轮事件验证”，读更新前的文字、增量和更新后的文字。

在事件选择器中选一条 `TEXT_MESSAGE_CONTENT`，展开“改一条事件，试运行 reducer”，只修改 `delta`，点击“验证并试运行事件”。下面的独立预览应改变，原回复保持原有内容。点击“结束回放，回到实时”恢复最新展示状态。

找到 `TEXT_MESSAGE_CONTENT`：同一条消息的 `messageId` 是否保持一致？`delta` 是追加还是整段替换？找到 `TOOL_CALL_END` 和 `TOOL_CALL_RESULT`：前者表示参数传完，为什么还需要后者？

打开 `shared/agui-agent.ts` → `shared/agui.ts` → `src/components/AguiChatTurn.tsx`，从事件发送、reducer 状态更新追到 React 渲染。

后面可以另发一条规划请求并点击“取消运行”，或输入“演示一次规划错误”，比较终止消息。主动中断 HTTP 与服务端确认取消是不同的结果。

## 10–20 分钟：声明怎样生成组件

在同一对话里发送：**“把这些出行需求做成一个可填写的表单”**。

新的回复会生成一张表单，初始目的地为杭州、天数为 3。打开生成过程的说明，对照组件声明、数据模型与实际渲染结果。检查器里可以找到 `createSurface`、`updateDataModel`、`updateComponents`。

填写姓名，把目的地改成成都，先不要提交。字段已改变，但没有业务 HTTP 请求：这是本地数据绑定。提交后检查 `action` 的 context，确认字段路径已解析成具体值；服务端通过更新消息修改表单中的结果文字。聊天也会追加这次界面操作和操作结果。

展开“声明如何变成 React 组件”，选择 `days` 声明，观察 `TextField.value.path` 如何找到模型值，再定位实际输入框。把 `Button.child` 看作组件 ID，找出该 ID 对应的文字组件。

展开“A2UI Workshop：改声明，观察同一个 renderer”，先预测本地绑定是否会改变组件声明，再运行实验。这里会改变当前表单的模型值；点击“重置为初始声明与模型”可恢复本轮初始状态。

想多走一步，可以载入“预算字段 + action.context”，点击“验证并应用到真实界面”，填写姓名和预算后提交。面板会核对预算是否进入真实 action 和服务端回显。随后再发“生成带预算和同行人数的出行表单”，比较服务端下发的组件结构。

打开 `shared/a2ui-agent.ts` → `shared/a2ui.ts` → `src/components/A2uiSurfaceRenderer.tsx`，看生成函数怎样产生声明、运行时怎样验证消息、`SurfaceRenderer` 怎样把白名单组件映射为 React；`src/labs/A2uiLab.tsx` 管理请求、trace 和表单绑定。生成的是组件与数据描述，浏览器不执行模型输出的任意代码。

## 20–30 分钟：工具怎样提供应用

继续发送：**“打开这个城市的活动应用”**。

应用应继承最近一次成功提交表单的城市；如果只完成基础流程，就是成都。它在新的 Agent 消息中打开，前面的表单仍然可操作。展开“工具为什么自带界面”，观察工具定义中的 UI 资源关联、`resources/read` 以及独立的 App 握手。

在嵌入式应用里选择上海。找到 App → Host 的工具请求，以及 Host → MCP Server 的请求。它们跨越不同边界，但属于同一次界面操作。工具返回的数据更新 iframe 中的活动列表，聊天也会显示操作结果。

展开“动手验证 MCP Apps 因果链”，先预测只换工具结果是否需要重读 UI 资源。在实验 A 中选择另一个城市，运行后应看到新增 1 次 `tools/call`，没有新增 `resources/read` 或 iframe 挂载。

再运行实验 B，读取另一份布局资源。应新增 1 次 `resources/read` 和 1 次 iframe 挂载，工具调用数不变，城市与活动数据保留。实验 A 只改变本轮 App；需要把城市带入后续对话时，在 App 内点击城市按钮。

切换深色模式，观察应用是否收到宿主主题。查看任意旧回复底部的协议按钮，确认检查器切换的是那一轮的消息。手机上检查器以抽屉打开，可用关闭按钮或 Escape 返回对话。

打开 `shared/mcp-server.ts` → `src/labs/McpLab.tsx` → `src/mcp-app.ts`，分别看工具资源、Host 和 iframe 应用的职责。这里用官方 App / AppBridge，Host 仅托管本项目的可信本地资源。

## 看懂聊天宿主

`shared/chat-agent.ts` 根据输入关键词或手动指定的协议选择回复方式，并解析城市和天数。它是教学用的确定性路由，不是 LLM，也不是三个协议的一部分。

`src/ChatWorkspace.tsx` 保存消息、每轮协议 trace 和共享旅行上下文。AG-UI 使用同一个 `threadId` 与此前对话；表单和应用通过交互回调把选择带回后续轮次。三种协议各自运行，聊天宿主把它们组织在同一对话中。

等待回复时可以先写下一句话。如果路由失败或超时，原消息会保留并显示错误，可点击“重试这条消息”；输入框里的新草稿（包括主动清空后的空白）保持不变。该重试重新选择并发起这一轮回复，不代表恢复已中断的协议执行；AG-UI 断流使用回复自身的重试入口，任务恢复实验则使用 checkpoint 与事件重放。

打开文档或实验遇到模块加载失败时，界面会给出“重试加载”和返回入口。检查连接后可以局部重试，其他工作区中已有的消息与草稿仍会保留。

## 关掉笔记，尝试回答

1. AG-UI、A2UI、MCP Apps 分别约定什么？
2. 哪部分是协议，哪部分是传输，哪部分是聊天产品自己的设计？
3. 为什么 A2UI 的组件由宿主渲染，MCP App 的界面由工具资源提供？
4. 如果把规则 Agent 替换为真实模型，哪些层应该保留？
5. 界面操作怎样更新数据，又怎样影响后续对话？

如果还说不清楚，选中一条实际消息，沿发送方与接收方再走一遍。通过顶部书本图标或回复底部的教程链接，在阅读器里打开 [从观察到独立开发](07-learning-method.md)，完成声明编辑、预算字段提交和工具数据 / UI 资源对比实验。“返回 Agent 对话”会保留当前消息、表单和 App。侧栏“独立实验与源码导读”可以进入专门的协议实验；返回聊天时消息、草稿和 App 仍在，聊天中进行的请求继续执行。也可通过浏览器后退返回上次独立实验并继续编辑。刷新或新建对话会清空当前聊天。

## 记录证据，再离开旅行示例

本次首次体验至少留下三项记录：

- 一条文本增量及它更新前后的文字，注明消息 ID 与实际运行模式
- 一次表单 action 及处理结果，说明填写时的本地绑定与点击后的动作边界
- 一次工具数据更新或 UI 资源切换，说明调用、资源读取与 iframe 挂载的变化

随后从 [练习清单](05-exercises.md) 选一个源码改动，再按 [独立项目：活动报名准备](08-independent-project.md) 定义新的输入输出和只读查询。该任务需要自己实现，不在本章 30 分钟体验内；完成契约、消息边界、失败保留和 P1–P8 人工验收后，才记录为此范围的独立交付。
