# 首次学习验收：任务与观察记录

本章为维护者提供首次学习验收方案，用 3 位符合受众的开发者检验入口、操作说明、协议边界和独立迁移任务是否可执行。任务卡、招募与排期材料、空白记录模板和单独的内部预演记录已就绪；尚未实际招募或观察首次读者，没有首次读者的完成时间、通过率或用户反馈结果。

## 先明确这轮要验证什么

项目面向能阅读 TypeScript、理解常规前端交互的开发者。首次验收要回答：读者能否找到学习入口，亲自改变一个输入，找到对应消息，并解释消息为什么改变界面。它不验证生产系统能力，也不以术语记忆或预测题答对次数代替实际操作。

分开记录两种证据：首次会话中的操作与解释，以及之后 [独立项目](08-independent-project.md) 的实现与人工验收。前者通过只说明读者走通了教学闭环；后者有实际交付和运行证据，才能说明完成了新场景迁移。

## 计划招募的 3 位读者

下表是待招募的席位条件，P01–P03 为预留匿名编号，不代表已经有对应参与者。首轮可以先完成其中 2 位，但应覆盖至少一位未接触 Agent UI 的前端开发者；样本规模用于发现卡点，不用于估计整体用户通过率。

| 预留编号 | 适合的经历                                                                | 要观察的重点                                                         |
| -------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| P01      | 能独立做 React / TypeScript 表单，理解 fetch，未使用过这三类协议          | 能否从聊天找到教程和检查器，把字段变化与消息联系起来                 |
| P02      | 熟悉 React 与业务 API 的全栈开发者，接触过流式响应但未做过 Agent UI       | 能否区分协议、HTTP / SSE、业务校验与页面状态，不把确定性规则当成 LLM |
| P03      | 做过常规聊天界面的前端开发者，可能用过某一种 Agent UI SDK，但未读过本仓库 | 能否解释声明、工具结果与 UI 资源的差别，迁移时避免沿用旅行专用契约   |

招募前询问实际技术背景、可用设备和是否读过本仓库。不把项目维护者或已经修改过这些学习面板的人当作首次读者；若使用熟悉仓库的同事做预演，明确记为“内部预演”，与首次读者记录分开。

## 准备一次可比较的首次会话

安排约 60 分钟：5 分钟记录背景与运行模式，15 分钟完成 T1，20 分钟完成 T2，15 分钟完成 T3，最后 5 分钟复述边界。这里是观察时间安排，尚无实际用时证据；时间到时记录做到哪一步，不替参与者补完后标记通过。开始任务前重置本次聊天与学习记录，保证观察到的是参与者自己的操作。

优先使用已经可访问的 Pages 学习版，让第一次观察集中在学习路径。若参与者已有本地运行环境，可以使用本地模式；记录版本、入口和模式，分别判断是否真的有 HTTP 请求。环境启动失败归入环境卡点，不计作协议理解失败。必要时暂停任务计时，记录暂停区间。

会话开始前，观察者应亲自确认所选入口可访问、任务按钮可用、样例输入与当前版本相符。这是执行前检查要求；本文没有代替观察者运行或确认这些检查。准备空白记录，询问是否允许记录屏幕或原话；不同意录制时只记去标识化的操作过程，不收集真实业务信息、账号或密钥。

让参与者从 [学习地图](README.md) 或 [第一次学习](00-first-session.md) 开始。先把下面任务卡发给参与者，预期证据和判定表由观察者留存，避免把答案提前展示给参与者。

## 参与者任务卡

### T1：解释一段文字如何出现

发送“帮我规划杭州三日游，喜欢慢节奏”。找到能观察回复生成过程的入口，在一条文本内容事件处比较更新前后状态。先口述改变 `delta` 的预测，再只改变它并试运行。

请展示改变后的预览、原回复，以及对应的原始记录。解释修改影响了哪一块界面，并找到负责事件更新与界面渲染的源码位置。可以查看教程、搜索和编辑器，不需要背诵函数名。

### T2：让一个新字段进入动作

继续同一段对话，生成普通出行需求表单。在学习面板中增加预算字段及其所需的模型、布局引用与动作绑定；可以使用项目提供的预设，但要解释四处如何对应。填写姓名，把预算改成 `4200`，提交表单并找到预算进入动作及结果的证据。

随后故意应用一个不存在的绑定路径，展示失败反馈以及保留的有效表单。打开相关教程再返回聊天，检查当前表单是否仍可操作。说明本地输入、应用声明、点击提交分别改变了什么，哪些步骤跨了当前运行模式中的边界。

### T3：区分工具数据、界面资源和业务事实

打开城市活动应用，先预测只换工具结果会触发哪些操作，再执行实验 A。接着换一份布局资源，执行实验 B。对照活动内容、计数与原始记录，说明两种操作为什么不同。

最后阅读 [独立项目：活动报名准备](08-independent-project.md)，写出一个有效业务输入、一个失败保留规则和协议选择理由。指出“可查看准备事项”是否说明报名已经发生，以及目前是否调用了真实活动 API 或 LLM。这一段只检查是否读懂作业要求，不要求在首次会话里写完项目。

## 观察者怎样判定任务完成

三个席位都做 T1–T3，不用不同题目替换核心步骤。可以按席位重点追问，但记录追问内容，避免把观察者讲解后的答案当成独立理解。

| 任务 | 必须出现的完成证据                                                                                                        | 不能据此判为通过的情况                                                         |
| ---- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| T1   | 实际文本事件、状态前后值、修改后的独立预览与原回复；能指出事件处理和渲染源码                                              | 只复述 `delta` 的定义，或只选对预测题，没有完成修改与定位                      |
| T2   | 预算 `4200` 同时出现在已解析的 action context 与处理结果；错误绑定被拒绝，最后有效表单仍在；文档往返保留表单              | 仅在输入框看到预算，或把本地绑定写入说成服务端动作；因有效校验失败而误称已成功 |
| T3   | 实验 A 的资源读取、iframe 挂载、工具调用增量为 `0 / 0 / 1`；实验 B 为 `1 / 1 / 0`；能关联原始记录并写出独立任务输入与边界 | 只背计数，不看活动数据与记录；把工具结果更新说成重新加载资源，或宣称已产生报名 |

本地 T2 应能找到 `/api/a2ui/action` 的往返；Pages 对应浏览器内动作处理，并标明 `browser-memory`。本地 T3 的 MCP 数据调用经过 `/mcp`，Pages 的核心 MCP 在浏览器内通信；两种模式的 App / Host 握手都跨 iframe。参与者按自己使用的模式解释正确即可。

任务结果只用下面五种状态，并另记提示级别：

| 状态       | 判定方式                                                       |
| ---------- | -------------------------------------------------------------- |
| 独立完成   | 操作证据齐全，解释正确，提示级别 H0                            |
| 提示后完成 | 操作与解释最终满足标准，但收到 H1 或 H2 提示                   |
| 未完成     | 实际尝试后缺少必需证据、解释仍错误，或到时未完成               |
| 环境阻断   | 入口、连接、模块加载或设备问题使任务无法继续；记录是否尝试恢复 |
| 未执行     | 尚未开始或本次没有安排，不计为通过或失败                       |

H0 表示未给导航或答案提示，观察者只重述任务并用“你现在在找什么”这类中性话语了解思路。H1 表示指向一个入口或章节，H2 表示给出具体操作顺序或解释，H3 表示观察者接管操作。出现 H3 后，参与者本次不记为完成；修复后安排新的尝试，保留两条记录。

参与者因卡点求助时，先记录停留位置、尝试和问题，再按 H1 → H2 提示；需要接管时才使用 H3。观察者不能替读者选择预测答案、修改 JSON 或寻找证据，然后写“独立完成”。

## 独立迁移另行验收

首次会话结束后，邀请愿意继续的参与者在自己的分支或项目里完成 [独立项目](08-independent-project.md)。允许查文档和代码；请记录使用的辅助工具及获得的帮助。若借助生成工具，还应让参与者自己修改一个业务输入、解释适配边界并执行失败恢复，不能只展示生成物。

用独立项目的 P1–P8 和提交物逐项验收，特别重放有效查询、失败保留、晚到响应。记录协议选择是否在当前支持范围内、业务输入是否独立于旅行模型、是否明确只读 fixture，以及后续参与者能否按说明复现。

迁移结果独立记录为“通过 / 未通过 / 未执行”。只有必验项都有实际通过证据，才记为通过；只有输入设计、口头解释或实现计划时记为未执行运行验收，不声称项目已经完成。若参与者没有时间继续，保留“未执行”，不能从 T3 的作业阅读推断迁移通过。

## 卡点分类与下一步动作

每次卡点选一个主要类别，必要时加次要类别。分类帮助决定修改位置，不代替对实际过程的描述。

| 类别       | 可观察的信号                                                | 后续处理                                               |
| ---------- | ----------------------------------------------------------- | ------------------------------------------------------ |
| 环境与连接 | 页面打不开、模块加载失败、请求超时、模式不匹配              | 记录入口与错误，验证恢复提示或启动说明；恢复后再测理解 |
| 入口与导航 | 反复找教程、检查器或返回入口，文档往返丢失操作位置          | 记录查找路径，检查入口文案与状态保留                   |
| 任务说明   | 找得到控件，却不清楚要改哪项、成功应看哪里                  | 补明确输入、操作目标与完成证据，再让新读者重做         |
| 消息与状态 | 把增量当替换、本地绑定当请求、资源读取当工具查询            | 回到同一条原始消息与前后状态，改进边界解释             |
| 源码与契约 | 无法从事件定位处理函数，或迁移时仍用旅行字段                | 补数据流线索、独立 schema 与适配说明                   |

| 范围与结论 | 把 fixture 当真实服务，把可查询当已报名，把局部得分当已掌握 | 修订模式、只读提示和完成标准，要求用事实复述           |

## 怎样形成一轮验收结论

逐任务填写每位参与者的状态、提示级别和证据，再汇总观察到的卡点与对应修订。人数、时间和通过数量只能从实际记录计算；样本未完成时写清分母与未执行项。没有实测时，本章结论始终是“验收方案就绪，读者验证待执行”。

首轮教材验收的判定目标是：至少 2 位符合条件的首次读者完成 T1–T3，其中至少 1 位为未接触 Agent UI 的前端开发者；三项均有操作和解释证据，未发现会阻止任务完成的实现问题。存在 H1 / H2 时，结论写“提示后走通”，列出需修订入口或说明，不能写“读者可独立完成”。

只有至少 2 位首次读者在 H0 下完成全部核心任务，才可报告“本轮样本独立走通首次学习路径”；只有独立项目实际通过，才另外报告完成迁移的人数。小样本结论限定在本轮参与者与该版本，不推广为所有读者都能完成。

修订后保留原记录，并安排同一步骤复测。已经看过提示的参与者复测只能证明问题得到恢复；若要验证首次可发现性，应另找未接触该任务的读者。每轮结论写明已验证、仍需提示与尚未执行的部分，不能把计划中的观察写成已取得的用户结果。
