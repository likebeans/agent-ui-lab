# 活动报名：恢复与确认联合实验

用一个活动报名任务，连接 A2UI 表单、版本化提议、人工确认、AG-UI 事件记录和可恢复的业务事实。

入口：[活动报名联合实验](/#labs/enrollment-workflow)。先完成[任务恢复](task-recovery.md)与[人工确认](human-approval.md)，再对照本实验理解组合时需要新增的联合契约。独立开发作业见[活动报名准备](../08-independent-project.md)。

## 场景与边界

报名内容包括姓名、工作坊和人数，全部使用教学样本。表单由 A2UI v0.9.1 的受支持组件生成。保存表单只创建或修改提议，明确确认后才写入本地报名记录，没有支付、外部 API 或真实活动报名。

本地模式将任务、命令收据、报名事实与 AG-UI 事件写入同一个 SQLite 事务。Pages 共用引擎，但使用当前页面内存。界面状态和恢复身份分开：sessionStorage 只保存会话、任务与待定命令，不保存权威任务快照或报名事实；浏览器禁止存储时当前操作仍可执行，刷新后不能自动找回身份。

本实验的事件通过 HTTP JSON 事实查询批量重放，**没有新增 SSE 长连接**。AG-UI 事件 payload 按官方 schema 验证；taskId、runId、seq 是记录关联层。表单与审批是应用层组合，没有把 A2UI 消息嵌入 AG-UI，也没有把既有 W1/W2 的两个任务简单当作同一个状态机。

## 联合身份与状态转换

| 身份或版本                   | 含义                           | 验证位置                           |
| ---------------------------- | ------------------------------ | ---------------------------------- |
| 教学会话                     | 当前任务归属；不是生产认证     | 命令与事实查询都核对               |
| taskId                       | 一次完整报名流程               | 表单、命令、事件、checkpoint、报名 |
| runId                        | 从首次提议直到确认或拒绝的运行 | 等待输入和修改内容时保持同一个值   |
| proposalId / proposalVersion | 被审阅的具体内容               | 每次保存修改增加内容版本           |
| task.version                 | 命令的并发前提                 | expectedVersion 必须匹配           |
| commandId                    | 一次不可变操作                 | 同键同参返回原收据；同键异参冲突   |
| seq                          | 已提交事件的连续序号           | 重复内容一致才去重，缺口拒绝       |

```text
尚无任务
  → 表单动作 + propose
  → waiting-input，创建 run，生成提议版本 1
  → edit：仍为 waiting-input，同一 run，内容版本 +1
  → approve：succeeded，报名事实和完成事件一同提交
  或 reject：cancelled，不生成报名事实
```

等待人工输入期间已有 `RUN_STARTED`、`STATE_SNAPSHOT` 与 `CUSTOM enrollment/proposal`，但没有 `RUN_FINISHED`。确认后，记录 `save_enrollment` 工具的参数与实际本地结果，再结束同一运行。工具事件描述已提交的本地写入；它不意味着模型调用了真实第三方工具。

## 实验一：确认前刷新恢复

1. 填写姓名、工作坊和人数，点击“生成待确认提议”。
2. 记录任务 ID、运行 ID、提议版本、事件游标与报名记录数，当前记录数应为 0。
3. 在本地模式刷新。页面按保存的身份查询事实，应恢复同一任务、run 和待确认内容。
4. 再次“查询事实并恢复”，游标和事件数量不增加。
5. 查看检查器中的 checkpoint 与事件，解释恢复为什么没有重新生成提议。

本地服务重启同样可从 SQLite 查询恢复，数据库重开和 HTTP 重启路径有自动化验证。Pages 刷新会清空事实：应显示任务不存在，不能把旧身份当作新模拟的有效任务，显式“开始新任务”后才继续。

## 实验二：旧确认不能授权新内容

1. 生成提议，展开“验证旧确认与丢失响应”，点击“保存当前确认命令”。
2. 修改人数并保存。观察提议版本增加，taskId 与 runId 保持不变。
3. 点击“发送保存的旧确认”。
4. 应收到 `VERSION_CONFLICT`，报名记录数保持 0，已保存的新内容仍显示。
5. 重新核对当前版本，再点击“确认此版本并报名”，记录数才变为 1。

草稿有未保存修改时不能确认。查询或保存冲突时发现远端新版本，又有本地草稿时，界面要求选择“采用已保存内容”或“保留草稿并重新保存”，不会静默覆盖。本地可复制标签页的同一会话与任务：一页改为 3 人，另一页先保存 4 人，再回到第一页保存，验证 `VERSION_CONFLICT` 后草稿仍为 3、已保存内容为 4；Pages 的独立标签页没有共享权威状态。

## 实验三：提交后丢失响应

1. 新建任务并生成提议。
2. 打开“模拟命令提交后丢失响应”，确认此版本。
3. 界面显示结果未知，并保留发送前保存的精确命令。它不会把连接失败当作报名失败。
4. 点击“查询事实并恢复”，应查询到一条报名、原命令收据和同一个 run 的完成事件。
5. 点击“重放最后命令”，应返回 `replayed: true`，报名 ID、事件游标、工具结果数量均不变。

待定命令只有查询之后才允许原命令重试。也可以在结果未知后刷新：本地会先查询原任务与收据，已提交时恢复事实；查询确认没有收据时，使用原会话、版本、参数、动作时间戳和命令 ID 重试。若是 Pages 刷新后事实已经清空，旧命令不会自动重放到新模拟；结束该次恢复后显式开始新任务。

恢复响应必须包含可完整应用的表单声明，且控件绑定、任务身份、版本与已保存内容一致。空声明、缺失组件或错误身份会被当作不完整结果，保留当前表单与待定命令，继续提供查询入口。

## 接口与源码

| 接口                                          | 输入                                                   | 结果                                                         |
| --------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------ |
| `POST /api/labs/enrollment-workflow/commands` | `{ command, action? }`；生成或修改必须匹配 A2UI action | 明确接受、版本冲突、拒绝，或传输结果未知                     |
| `GET /api/labs/enrollment-workflow/facts`     | taskId、可选 commandId、runId、afterSeq                | 同一事务读取的任务、checkpoint、事件后缀、表单声明与报名事实 |

请求使用 `X-Teaching-Session` 教学身份。`X-Workflow-Drop-Response: 1` 仅用于在事务提交后丢弃响应。生产接入仍需服务端身份认证和权限校验。

源码入口：

- `shared/labs/enrollment-workflow/engine.ts`：复用人工确认引擎，并在外层事务记录执行事件。
- `shared/labs/enrollment-workflow/surface.ts`：生成声明，核对动作与业务命令的一致性。
- `server/labs/enrollment-workflow/store.ts`：独立命名空间，复用 SQLite 确认存储，原有实验数据互不混用。
- `src/labs/enrollment-workflow/client.ts`：完整响应超时、契约校验、精确命令与恢复身份。
- `src/labs/enrollment-workflow/Lab.tsx`：草稿、已保存提议、待定命令和已核实事实的交互。

## 完成证据

保留一组连续证据：生成提议的 A2UI action、等待输入的状态事件、内容修改后的版本、旧确认冲突、丢失响应时的待定命令、事实查询结果、原命令重放后的相同报名 ID 和游标。解释这组证据分别证明了什么。

本地事务只保证本地记录一致，不保证任意外部服务 exactly-once。真实 API 写入仍需下游幂等键、业务唯一约束或可查询的外部操作身份。接入真实数据源或模型时，继续保留确定性路径并先验证只读查询。
