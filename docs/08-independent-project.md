# 独立项目：活动报名准备

本章面向已经完成聊天学习实验的前端开发者，要求你用新的业务契约实现只读“活动报名准备”，交付可运行源码、协议记录和人工验收证据。下面提供任务规格与脚手架建议；示例数据均为教学 fixture，本章没有新增可直接调用的真实业务 API 或 LLM。

## 先确定要交付的功能

用户选择活动、参加人数和参与方式，点击“查看准备事项”，得到样本名额说明与准备清单。页面必须说明“教学样本，查询不保留名额，也不产生报名”。不要收集姓名、手机、支付信息，也不实现确认报名、审批或持久化写入。

完成任务后，你应能展示三个动作：修改一个输入，追踪它产生的消息；收到有效结果，让对应区域更新；制造失败，保留草稿和最后有效结果并恢复操作。只替换旅行表单的标题和字段文案不能满足任务要求。

先完成 [动手学习指南](07-learning-method.md) 的事件修改、预算字段提交、工具数据与资源对比。可以参考 [活动报名联合示例](labs/enrollment-workflow.md) 和[联合实验入口](#labs/enrollment-workflow) 理解组合后的边界，再关闭参考实现，按本章独立定义的数据契约完成作业。联合示例的实现与步骤以它自己的教程为准。

## 1. 固定自己的业务数据契约

先写契约，再写组件。下面的 ID、样本和规则是本次作业的固定验收输入，不需要请求外部活动平台。

### 只读样本

| `eventId`        | 活动名称       | 支持的 `attendanceMode` | `availableSeats` | 准备事项                     |
| ---------------- | -------------- | ----------------------- | ---------------- | ---------------------------- |
| `ui-foundations` | 交互界面工作坊 | `onsite`                | 5                | 携带电脑；提前 10 分钟到场   |
| `remote-intro`   | 线上协议导读   | `online`                | 8                | 准备耳机；提前检查浏览器音频 |
| `state-clinic`   | 状态排查小组   | `onsite`                | 0                | 等待下一期活动信息           |

`onsite` 显示为“现场”，`online` 显示为“线上”。名额数是样本中的固定值，每次查询都不扣减；重复查询不能被解释为占位或报名成功。

### 输入与关联身份

业务输入 `EnrollmentPrepInput` 只包含三项：

| 字段             | 类型与约束            | 验证责任                       |
| ---------------- | --------------------- | ------------------------------ |
| `eventId`        | 上表中的单个字符串 ID | 可信查询边界验证白名单         |
| `attendeeCount`  | 1–3 的整数            | 可信查询边界验证类型和范围     |
| `attendanceMode` | `onsite` 或 `online`  | 先验证枚举，再判断活动是否支持 |

请求使用应用层信封 `{ contractVersion, queryId, input }`。`contractVersion` 固定为 `"1"`；`queryId` 是每次执行新建的非空字符串，用于关联请求、结果与过期响应，不能用它代表用户、报名记录或协议 run。

这是一次有效的应用层查询输入：

```json
{
  "contractVersion": "1",
  "queryId": "prep-001",
  "input": {
    "eventId": "ui-foundations",
    "attendeeCount": 2,
    "attendanceMode": "onsite"
  }
}
```

### 成功结果与业务不可用

成功响应使用 `{ contractVersion, queryId, data }`，回显请求的版本与查询 ID。`data` 是业务结果 `EnrollmentPrepResult`，字段如下：

| 字段                      | 类型与规则                                                                 |
| ------------------------- | -------------------------------------------------------------------------- |
| `eventId`、`eventTitle`   | 来自已验证的样本记录                                                       |
| `input`                   | 本次规范化后的 `EnrollmentPrepInput`，用于说明结果对应哪次选择             |
| `status`                  | `ready` 或 `unavailable`；都表示查询成功，均不表示报名成功                 |
| `availableSeats`          | 样本名额，非负整数                                                         |
| `checklist`               | 非空字符串数组，按样本顺序显示                                             |
| `reason`                  | `ready` 时为 `null`；不可用时为 `unsupported-mode` 或 `insufficient-seats` |
| `source`、`deterministic` | 固定为 `local-fixture` 与 `true`                                           |

对有效输入先判断参与方式，再判断 `attendeeCount <= availableSeats`。方式不受支持时返回 `unavailable / unsupported-mode`；人数超出样本名额时返回 `unavailable / insufficient-seats`；其余返回 `ready / null`。这两类不可用结果仍包含活动信息和清单，页面明确显示原因，不能改写成系统错误。

上面的请求应得到以下成功响应：

```json
{
  "contractVersion": "1",
  "queryId": "prep-001",
  "data": {
    "eventId": "ui-foundations",
    "eventTitle": "交互界面工作坊",
    "input": {
      "eventId": "ui-foundations",
      "attendeeCount": 2,
      "attendanceMode": "onsite"
    },
    "status": "ready",
    "availableSeats": 5,
    "checklist": ["携带电脑", "提前 10 分钟到场"],
    "reason": null,
    "source": "local-fixture",
    "deterministic": true
  }
}
```

例如查询 `state-clinic`、1 人、现场，成功响应应明确不可用：

```json
{
  "contractVersion": "1",
  "queryId": "prep-003",
  "data": {
    "eventId": "state-clinic",
    "eventTitle": "状态排查小组",
    "input": {
      "eventId": "state-clinic",
      "attendeeCount": 1,
      "attendanceMode": "onsite"
    },
    "status": "unavailable",
    "availableSeats": 0,
    "checklist": ["等待下一期活动信息"],
    "reason": "insufficient-seats",
    "source": "local-fixture",
    "deterministic": true
  }
}
```

### 非法输入与执行失败

失败响应使用 `{ contractVersion, queryId, error }`，其中 `error` 包含 `code` 与面向用户的 `message`。固定区分 `INVALID_INPUT`、`QUERY_FAILED`、`INVALID_RESULT`；非法结构、未知活动、越界人数属于第一类，受控模拟的执行失败属于第二类，响应 schema 不符或关联身份不符属于第三类。能解析请求身份时回显原 `queryId`；若信封本身缺少有效身份，先拒绝执行，由调用方关联本地校验错误，不伪造成功响应。

例如把人数改为 `0`，应得到失败结果，不返回 `data`：

```json
{
  "contractVersion": "1",
  "queryId": "prep-002",
  "error": {
    "code": "INVALID_INPUT",
    "message": "参加人数必须是 1–3 的整数"
  }
}
```

`INVALID_RESULT` 也可以由调用方在校验候选响应或声明时产生，此时记录为本地错误，不能冒充查询边界发出的失败响应。

在实现中用运行时 schema 验证输入与结果，拒绝额外字段。若只用浏览器 fixture，所谓查询边界仍在浏览器内，只能证明教学验证逻辑；接入真实服务后，服务端必须独立验证，不能依赖客户端校验。页面中的推荐文案、Agent 决策或协议 schema 都不能替代这些业务规则。

## 2. 选择有用的协议能力

建议先选 **A2UI v0.9.1**：任务的重点是可填写表单、绑定与只读动作。只使用当前项目的六组件子集，不增加日期选择器、任意 HTML 或模型生成的 React 代码。协议版本、字段与目录限制见 [A2UI 教程](02-a2ui.md)。

如果已有明确学习目标，也可以改选下面的路径；提交时说明选择理由，并满足相同的业务契约和失败验收：

| 选择                                           | 本次具体用途                                   | 需要保留的边界                                                                        |
| ---------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------- |
| A2UI v0.9.1                                    | 服务给出表单结构，用户 action 触发准备事项查询 | 业务信封与 A2UI 消息分开验证，不给协议添加自定义顶层字段                              |
| AG-UI 1.0，项目使用 `@ag-ui/core@1.0.3`        | 展示查询过程、工具结果和最终状态               | 沿用受支持事件与生命周期，为活动数据定义独立状态投影，不假设旅行 reducer 能接收新状态 |
| MCP Apps 2026-01-26，项目使用 `ext-apps@2.0.3` | 只读工具提供独立交互应用                       | 注册自己的工具、结果 schema、受控 UI 资源与 Host allowlist，保留文本降级结果          |

完成一个选择就足够。若组合多个协议，必须交付封装契约和端到端消息证据；仅把多个面板放在同一页不能证明协议已经互相集成。先不引入聊天路由、LLM、长期记忆或写入审批。

## 3. 把 A2UI 动作适配到业务输入

推荐路径使用 Surface `enrollment-prep`，组件根 ID 为 `root`。初始化仍按 `createSurface` → `updateDataModel` → `updateComponents`，沿用项目固定的 Basic Catalog。表单模型与业务输入分开：

| 模型路径                | 初始值               | 控件或用途                        |
| ----------------------- | -------------------- | --------------------------------- |
| `/form/eventId`         | `["ui-foundations"]` | `ChoicePicker`，选项为三个活动 ID |
| `/form/attendeeCount`   | `"2"`                | `TextField`，输入保留字符串       |
| `/form/attendanceMode`  | `["onsite"]`         | `ChoicePicker`，选项为现场、线上  |
| `/result/summary`       | `"尚未查询"`         | 绑定结果摘要的 `Text`             |
| `/result/checklistText` | `""`                 | 绑定清单文字的 `Text`             |

使用 `Card`、`Column` 组织布局，按钮 ID 为 `check-preparation`，按钮的 `Text` 子组件显示“查看准备事项”。按钮 event 名为 `check_enrollment_preparation`，context 的三个字段分别绑定三个 `/form/...` 路径。所有模型路径必须在应用组件前存在。

点击按钮后，A2UI action 中是已解析的表单值：

```json
{
  "version": "v0.9.1",
  "action": {
    "name": "check_enrollment_preparation",
    "surfaceId": "enrollment-prep",
    "sourceComponentId": "check-preparation",
    "timestamp": "2026-10-26T09:00:00.000Z",
    "context": {
      "eventId": ["ui-foundations"],
      "attendeeCount": "2",
      "attendanceMode": ["onsite"]
    }
  }
}
```

这是本作业需要生成的动作样例，现有旅行动作接口并不支持这个动作。不要把它直接发给 `/api/a2ui/action` 并假定业务已经接通。

适配器先验证版本、Surface、来源组件、动作名和 context 结构。两个 `ChoicePicker` 都必须恰好选中一个白名单值；人数必须完整匹配 `1`、`2` 或 `3`，再转成数字，不能用 `parseInt("2人")` 接受非法输入。之后创建新的 `queryId`，组装第 1 节的业务信封。

查询结果验证通过后，由受控 builder 生成只更新 `/result` 的 `updateDataModel`，并保存对应的 `data.input`。不要用旧请求快照替换当前 `/form`。`status: ready` 显示“可查看准备事项（教学样本，未报名）”；`unavailable` 显示具体原因；两种结果都显示查询时的活动、人数与方式。用户继续编辑时，保留原结果并提示“当前草稿尚未查询”。

## 4. 写清消息与状态的归属

在提交物中画出或列出下面这条链路，并为每一步附一条实际记录。采用其他协议时替换协议一列，业务契约不变。

| 步骤     | 发送方 → 接收方           | 内容与状态责任                                         |
| -------- | ------------------------- | ------------------------------------------------------ |
| 修改控件 | 控件 → 本地模型           | 更新 `/form`，记录为本地绑定，不伪装成服务端消息       |
| 点击按钮 | Renderer → 动作适配器     | A2UI `action`，context 是点击时解析的值                |
| 发起查询 | 适配器 → fixture 查询边界 | 应用层版本、`queryId` 与规范化输入；该边界验证业务规则 |
| 收到结果 | 查询边界 → 调用方         | 成功 `data` 或失败 `error`，校验版本、身份和结构       |
| 更新视图 | 受控 builder → Renderer   | 验证整个消息批次后才应用；只改结果区域                 |

单独保存 `draft`、当前待处理的 `queryId`、查询阶段和 `lastSuccess`。查询阶段至少区分未开始、执行中、成功、失败；`lastSuccess` 关联自己的输入快照，不能被“正在查询”或错误提示覆盖。

先确认响应的 `queryId` 与发出它的那次请求相符，再判断该请求是否仍为当前查询。合法的旧请求按过期结果忽略；响应身份与原请求不符才是 `INVALID_RESULT`，也不能因此覆盖更新查询的状态。

应用身份放在 trace 的外层元数据或业务信封，原 A2UI payload 保持协议形状。浏览器内 fixture 的记录标为本地模拟；如果以后接入本地 HTTP，请分别标明请求与响应方向。本地函数调用记录、HTTP 请求和 iframe 消息不能混为一条网络证据。

## 5. 先约定失败保留与重试

为人工验收提供可重复的开发入口，例如“下一次查询失败”“下一次结果含非法组件”“延迟本次响应”。这些入口是学习用故障注入；提交说明必须给出触发和恢复办法，不依赖随机失败。

| 情况                                  | 应出现的结果                                   | 必须保留的状态                                            |
| ------------------------------------- | ---------------------------------------------- | --------------------------------------------------------- |
| 输入非法                              | 明确字段错误，不执行 fixture 查询              | 所有草稿值、最后有效结果与有效 Surface                    |
| fixture 查询失败或超时                | 显示失败和“用当前输入重试”入口，不显示报名成功 | 草稿、`lastSuccess` 和原输入快照                          |
| 结果 schema、关联身份或 A2UI 声明非法 | 拒绝整个候选更新，指出校验失败                 | 最后有效 Surface、草稿、`lastSuccess`；待处理状态能够结束 |
| 旧查询晚到                            | 记录为过期结果，不改当前查询阶段和界面         | 最新查询结果与最新草稿                                    |
| 卸载后回调到达                        | 取消或忽略回调，不继续写界面                   | 已销毁界面不再产生更新                                    |

A2UI 消息批次先在候选状态上完整验证，再一次性提交；不要先清空结果或把半批消息画出来。非法声明的注入可使用未知组件或缺失引用，不能让故障破坏保留的有效对象。

“用当前输入重试”重新读取并验证当前草稿，创建新的 `queryId`。它是一次新查询，不是事件重放或恢复原 run。用递增序号或当前查询身份忽略旧请求的成功与失败；仅中止 fetch 不足以覆盖已排队回调。为了验收晚到结果，允许在前一查询等待时发起下一查询。

如果选 AG-UI，还要模拟终止事件前断流，展示未完成并保留最后有效投影；不能因为 HTTP 200 就判定查询成功。如果选 MCP Apps，还要模拟工具失败与 UI 资源读取失败，保留有效数据并提供重开入口。不要把这些额外故障假称为 A2UI 本身的流式能力。

本作业默认状态只在页面内存中保存。阅读文档再返回可以按自己的宿主设计保留；刷新与关闭页面后允许清空，但必须在交付说明中写明。页面内存不能被表述为服务端持久化。

## 6. 从最小脚手架开始

下面是建议新建的路径，**本章没有创建这些业务实现**。采用 `enrollment-prep` 作为独立作业 ID，避免与参考联合示例的 `enrollment-workflow` 混用。

| 建议路径                                  | 责任                                                                     |
| ----------------------------------------- | ------------------------------------------------------------------------ |
| `shared/labs/enrollment-prep/contract.ts` | 输入、输出、错误的运行时 schema 与类型                                   |
| `shared/labs/enrollment-prep/fixtures.ts` | 第 1 节的三条只读样本                                                    |
| `shared/labs/enrollment-prep/engine.ts`   | 规范化输入、只读查询、结果验证与受控消息 builder                         |
| `src/labs/enrollment-prep/Lab.tsx`        | 表单、请求身份、状态保留、重试与故障注入                                 |
| `src/labs/enrollment-prep/manifest.ts`    | 按 [实验接入约定](labs/foundation.md) 注册；需先完成有效元信息与加载组件 |

先用浏览器内异步 fixture 调用完成验收，显式标注运行模式。此时不需要 Express 路由、MCP Server 或模型 SDK；有一层异步边界，已经可以验证加载、失败与乱序响应。

可复用 `shared/a2ui.ts` 的协议校验、消息应用和绑定工具，以及 `src/components/A2uiSurfaceRenderer.tsx`。动作业务校验和结果投影由新模块承担，不复用旅行专用动作校验器。manifest 的类型与生命周期见 `src/labs/types.ts` 和 [W0 教程](labs/foundation.md)。

如果决定补本地 HTTP，把新路由规划为 `POST /api/labs/enrollment-prep/query`，并按 W0 约定分别登记本地与静态 handler；这个路径是后续实现建议，当前仓库没有因此获得该接口。两种模式调用同一契约和只读 engine，Pages 仍明确标为浏览器内模拟。真实活动 API 与 LLM 接入留到 [真实开发路径](04-real-development.md)。

## 7. 按步骤执行人工验收

先记录提交版本、启动入口、浏览器和运行模式。下面是完成作业后需要执行的步骤；每项记录实际结果与证据位置，未运行的项目写“未执行”。本章不预填通过结果。

| 编号                  | 操作                                                                                                                            | 预期结果与应保留的证据                                                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| P1 有效查询           | 选择交互界面工作坊、2 人、现场，点击查询                                                                                        | A2UI action 对应数组、字符串模型值；业务输入为标量和数字；结果 `ready`、样本名额 5、清单两项；界面明确未报名                   |
| P2 本地编辑           | 在 P1 成功后把人数改为 3，不点击查询                                                                                            | 没有新增查询；上次结果仍对应 2 人；当前草稿提示尚未查询                                                                        |
| P3 业务不可用         | 先查询状态排查小组、1 人、现场；再查询线上协议导读、1 人、现场                                                                  | 前者 `unavailable / insufficient-seats`；后者 `unavailable / unsupported-mode`；两次都是成功查询，均未新增报名                 |
| P4 非法输入           | 通过故障入口或直接调用新查询边界提交人数 `0`，再提交未知活动 ID                                                                 | 两次均返回 `INVALID_INPUT`，不读取未知样本；从边界提交非法数据也不能绕过验证；有效界面与草稿保持                               |
| P5 执行失败与恢复     | 先完成 P1，再改成线上协议导读、1 人、线上；触发下一次查询失败；随后用当前输入重试                                               | 失败时保留新草稿和 P1 结果；新查询 ID 的重试成功，结果为线上活动、`ready`、名额 8                                              |
| P6 非法候选更新       | 先保留一个有效结果，触发非法结果字段或错误关联身份，再触发未知组件或缺失引用的 A2UI 更新                                        | schema、身份与声明校验各有拒绝记录；整批候选未被应用，草稿和最后有效视图保持，无无限加载                                       |
| P7 晚到响应与继续编辑 | 延迟查询 A：工作坊、1 人、现场；随后发起查询 B：线上导读、2 人、线上；B 等待时把草稿人数改为 3，不再查询；先让 B 成功，再释放 A | 结果仍对应 B 的 2 人输入，草稿为 3 人并提示尚未查询；A 的晚到成功被忽略；再用晚到失败重复一次，不能覆盖 B 的成功状态或后续草稿 |
| P8 清理与重置         | 查询等待时离开并卸载作业界面，再释放回调；重新打开后刷新页面                                                                    | 卸载后无旧界面更新；刷新后的行为符合内存范围说明；重复查询前后样本名额不变                                                     |

P6 中应分别执行结果 schema 错误、关联身份错误和声明错误，不能以其中一种代替其余。改选 AG-UI 或 MCP Apps 时，P1 保存对应的事件输入或工具参数；控件类型由自己的前端定义，不要求使用 A2UI 数组模型。用对应的非法事件或无效资源替代 P6 的声明错误，并补第 5 节的协议特有故障。

P8 的卸载使用切换到另一个独立实验或关闭自己挂载的组件；仅打开文档可能只是隐藏，不能当作卸载证据。

## 8. 交付什么，怎样判断完成

提交物放在你自己的作业分支或独立项目中，至少包含以下内容：

1. 可运行源码及启动、停止、重置说明，注明浏览器 fixture、本地 HTTP 或其他实际运行方式。
2. 输入、输出、错误契约和三个样本；说明业务不可用与执行失败的区别。
3. 一份协议选择说明，附 P1 的实际输入、原始协议动作、业务结果和界面更新记录。
4. P1–P8 的人工验收表，逐项填写“通过 / 未通过 / 未执行”、证据位置与遗留问题；额外协议故障也要记录。
5. 一段边界解释：谁验证业务、谁拥有草稿、结果对应哪份输入、旧响应为何不能覆盖新结果、刷新后什么会丢失。

另一位开发者应能按启动说明进入作业、重放 P1、P5、P7，并从证据找到对应查询。全部必验项有实际通过证据，且你能不照抄旅行术语解释这五个边界，才达到本章的独立迁移完成标准。只提交截图、预测题分数或设计稿都不足以替代运行证据。

若暂时只完成设计，明确标为“契约与实现计划已完成，运行验收未执行”，不要宣称已经独立开发完成。需要检验教材是否让首次读者走到这一步，可使用 [首次学习验收任务与观察记录](09-learning-validation.md)。
